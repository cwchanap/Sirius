# HPA-384 Save/Load Responsive Cards Implementation Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Replace the runtime-built `SaveLoadDialog` with a scene-authored, responsive Sirius Save/Load card screen while preserving the current SaveManager, Main Menu, Pause, load-handoff, backup-recovery, and scene-transition behavior.

**Architecture:** Add one `SaveLoadScreen.tscn` + `SaveLoadScreenController` vertical slice. `SaveManager` gains only an explicit metadata `SaveSlotState` so the UI can distinguish corrupted from newer-version saves. Main Menu and Game keep their explicit `UIScreenHost` integrations and domain handlers; they only swap the concrete view. No save facade, reusable card component, host factory, navigation service, or shared confirmation framework is introduced.

**Tech Stack:** Godot 4.6.2, C#/.NET 8, GdUnit4, existing Sirius Theme / `SiriusModalShell` / `UIScreenHost`.

**Design:** `docs/superpowers/specs/2026-08-11-hpa-384-save-load-design.md`

private bool CanActivateSlot(int slot, SaveSlotInfo info)

`OnSlotPressed(int slot)` must preserve the current overwrite rule:

## Implementation review checklist

Before marking HPA-384 implementation ready for merge, verify the resulting diff still obeys these boundaries:

- `SaveManager` owns file I/O, version checks, atomic write, and backup recovery.
- `Game` owns gameplay save eligibility and save-data collection.
- `MainMenu` / `Game` own load handoff and scene transition.
- `SaveLoadScreenController` owns presentation, action availability, overwrite child, and terminal intent only.
- Main Menu and Pause each keep their existing local `UIScreenHost`; there is no shared Save/Load host factory.
- No Delete UI exists.
- No thumbnails, playtime, extra slots, cloud saves, renaming, auto-repair UI, or fabricated metadata exists.
- No generic save-card component or save view-model framework exists.
- No HPA-572 shared confirmation/error framework is implemented as part of this ticket.
- Compact 640×360 is scrollable and usable; standard 1280×720 is 2×2 and readable.
- Disabled cards give a readable reason.
- Child Cancel closes overwrite before Save/Load.
- All terminal paths are one-shot.

## Planned implementation sequence

1. **Save metadata classification** — explicit Empty/Valid/Corrupted/Incompatible state, no behavior change.
2. **Isolated screen** — author and fully test the responsive card screen before any production cutover.
3. **Main Menu Load cutover** — replace only its concrete hosted view.
4. **Pause Save/Load cutover** — replace the second concrete host, delete the legacy dialog, update lifecycle evidence, and run full verification.

This sequence keeps every intermediate commit buildable and avoids mixing persistence changes, UI authoring, and both host migrations into one review step.
